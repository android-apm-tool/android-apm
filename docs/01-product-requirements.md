# 제품 요구사항

## 목적

Android 앱에서 사용자가 접근할 수 있는 화면과 접근 방법을 발견한다. 선택한 화면 상태까지의 실행 흐름, 함수 호출, 외부 연결, 자원 사용량과 측정 조건을 함께 보여준다.

사용자는 프로젝트에 플러그인을 적용하고 APM 작업을 실행한다. 수집 결과는 개발 머신의 localhost에서 확인한다.

## 용어

| 용어 | 정의 |
| --- | --- |
| 화면 | 사용자가 접근 가능한 앱의 화면 단위 |
| 화면 정의 | 코드에서 식별한 목적지 또는 독립 화면 콘텐츠의 정의. 실제 접근 가능성과 실행 여부는 별도 상태 |
| 화면 후보 | 화면 경계·역할 또는 연결 해석이 끝나지 않은 UI 콘텐츠. 정의로 확정하기 전에도 보존 |
| 화면 상태 | 동일 화면의 로딩·콘텐츠·빈 결과·오류 등 구분 가능한 상태 |
| 유저 로드 | 화면 단위를 모아 사용자가 선택한 분석 범위 |
| 인바운드 경로 | 특정 화면 상태로 진입하는 방법. 출발 화면, 동작, 조건, 외부 진입점 등을 포함 |
| 트레이스 | 유저 로드의 특정 화면 상태까지 골라 실행 흐름, 외부 연결, 측정값, 측정 조건을 확인하는 분석 단위 |
| entry 선언 | Nav3 키와 콘텐츠를 연결하는 등록 또는 `NavEntry` 생성 지점 |
| 화면 인스턴스 | 실행 중 특정 탐색 영역에서 생성된 실제 화면. 같은 화면 정의의 여러 인스턴스를 구분 |

entry 하나가 화면 상태 전체를 표현한다고 가정하지 않는다. 화면 내부 상태 분석과 관측을 별도로 연결한다.

## 지원 목표와 첫 구현 범위

- AGP 9.0, Android 8.0 이상, compileSdk와 targetSdk 모두 36 이상.
- 첫 탐색 엔진은 Compose + Nav3를 대상으로 한다.
- XML Navigation과 Fragment Navigation 어댑터는 첫 구현 범위에서 제외한다.
- AndroidManifest 권한과 Android RES 분석은 유지한다. XML Navigation 제외가 XML 파일 전체의 제외를 뜻하지 않는다.
- 선택한 앱 variant의 소스 모듈과 생성 소스를 분석한다.
- 대상 소스의 전체 Composable 선언을 수집하고, 모든 Compose UI 진입점과 Nav3 provider에서 콘텐츠 연결을 추적한다. MainActivity나 Nav3 entry 내부로 검색을 한정하지 않는다.
- Nav3 밖에서 조건·상태로 교체하는 Compose 콘텐츠도 화면 후보로 수집한다. ComposeView 등 호스팅 진입점 발견과 XML/Fragment 탐색 경로 분석은 별도 지원 항목이다.
- SDUI가 서버 데이터로 만드는 개별 화면은 정적 화면 정의 발견률의 대상에서 제외한다. 프로젝트에 있는 SDUI 렌더러·호스트 코드는 수집하되 서버 화면 전체를 발견한 것으로 세지 않는다.
- 다른 variant, 외부 바이너리 내부 코드, 동적 목적지, 사용자 정의 탐색 방식의 지원 여부는 별도로 기록한다.

장기 목표는 모든 사용자 접근 가능 화면·경로의 자동 분석이다. 첫 구현은 전체 선언 수집과 UI·Nav3 연결을 결합해 최대한 많은 화면 정의를 발견하고, 미해결 연결과 미분석 범위를 명시해야 한다. 실제 접근 가능성과 실행 가능성은 선언 발견과 별도로 검증한다.

## 화면 발견의 완료 기준

- 지원 범위를 먼저 고정한 평가 집합에서 **화면 정의 발견률 99% 이상**을 목표로 한다. 현재 수집기 구현과 발견률 측정 결과는 없다.
- 등록된 키와 콘텐츠, 루트 밖의 선언, 조건부 콘텐츠를 보존한다. 루트 연결 실패나 실행 미관측을 이유로 후보를 제거하지 않는다.
- 화면·상태·컴포넌트 분류 근거를 제공한다. 함수명에 `Screen`이 있거나 `@Composable`이라는 이유만으로 화면으로 확정하지 않는다.
- 화면 정의 발견률, UI 루트·provider·콘텐츠 연결 해석률, 전환 경로 발견률, 화면 판정의 정밀도를 별도 측정한다. 화면을 찾았다는 사실을 접근 경로까지 찾았다는 의미로 사용하지 않는다.
- 선택 variant, 입력 모듈, 지원 버전·패턴, SDUI 등 제외 범위와 미해결 건수를 표시한다. 정답 목록이 없는 사용자 프로젝트에 추정한 99%를 표시하지 않는다.

분모, 정답 판정, 중복·오탐 처리와 보고 형식은 [검증 계획](06-validation-plan.md)에 따른다.

## 확정된 화면 구성

### 1. 유저 로드 지도

- 화면을 노드로, 화면 전환을 방향 간선으로 표현한다.
- 노드 왼쪽에는 화면 UI, 오른쪽에는 클릭 가능한 상태 목록을 배치한다.
- 상태 개수만 표시하지 않고 로딩·콘텐츠·오류 등 개별 상태를 선택할 수 있게 한다.
- 화면을 선택하면 그 화면을 루트로 하는 상태 트리를 탐색한다.
- 화면들을 선택해 유저 로드의 범위를 정한다.
- 같은 두 화면 사이의 여러 접근 방법은 데이터에서 분리하고, 지도에서는 묶거나 펼칠 수 있게 한다.
- 미분류 화면 후보와 연결 미해결 항목은 근거와 함께 검토할 수 있게 한다. 화면 상태·컴포넌트와 UI 구성 간선을 확정된 화면 전환으로 표시하지 않는다.

### 2. 인바운드 경로 및 디바이스별 트레이스

- 선택한 화면 상태로 들어오는 접근 방법을 한 페이지에서 확인한다.
- 해당 경로들의 측정값, 시간에 따른 자원 변화, 측정 기기 성능 정보를 함께 배치한다.
- 디바이스를 트레이스의 측정 조건으로 선택한다. 여러 기기에서 수집된 결과임을 식별할 수 있어야 한다.
- 경로를 클릭하면 함수 호출 및 자원 시계열을 연다.
- 현재 프로젝트의 결과를 중심으로 보여준다. 수정 전후 비교 화면과 별도 실행 기록 창은 확정 범위에 포함하지 않는다.

### 3. 함수 호출 및 자원 시계열

- 왼쪽에 사용자 UI를 표시하고 각 컴포넌트의 완료 시점을 시간축에 화살표로 연결한다.
- 함수 호출은 실행 인스턴스별로 모두 나열한다. 반복 호출을 호출 횟수 하나로 대체하지 않는다.
- 함수 막대의 가로 위치는 시작 시점, 길이는 경과 시간이다.
- 호출의 부모·자식 관계와 코루틴·병렬 실행 관계를 함께 표현한다.
- 반복을 풀어 표시한 행에 의미 없는 `1회` 표시는 넣지 않는다.
- 우측 CPU·메모리·RAM·디스크·힙 등의 시계열은 지표별로 완전히 분리된 행을 사용한다.
- 함수를 선택하면 해당 호출 구간을 모든 관련 그래프에서 같은 시간 범위로 강조한다.
- TTFD, TTFB, 외부 API 정보는 관련 호출·이벤트에 연결한다.
- 실행 흐름을 외부 API까지 이어서 보여준다. 별도의 중복 함수 호출 그래프 화면은 만들지 않는다.

### 4. 구성 탐색

- 빌드 의존성을 유저 로드 지도와 같은 탐색 방식의 방향 그래프로 표시한다.
- 그래프 노드는 프로젝트 내부 모듈만 사용한다.
- 외부 패키지는 모듈을 클릭했을 때 확인한다.
- 우측 패널에서 권한, Android RES, 테스트 구성을 함께 확인한다.
- 정보는 선택한 variant와 모듈에 연결한다.

## 수집·표시할 정보

| 영역 | 요구 정보 | 측정·해석 기준 |
| --- | --- | --- |
| 함수 | 각 호출, 시작·종료, 소요 시간, 부모 관계 | 호출 인스턴스를 보존하고 집계는 파생값으로 계산 |
| 비동기 | 코루틴, 병렬 분기, 대기·재개·취소 | 논리적 작업과 실제 스레드 실행 구간을 구분 |
| 화면 | 접근 방법, 상태, UI 컴포넌트 완료, TTI | 화면 준비 조건과 완료 판정 규칙을 명시 |
| 시작·표시 | TTFD 및 화면 완성 시점 | Android 앱 시작 TTFD와 일반 화면 완료 지표의 범위를 구분 |
| CPU | 사용률, 제공 가능한 CPU 시간 | 프로세스·스레드 범위와 정규화 기준을 명시 |
| 앱 메모리 | PSS 등 제공 가능한 사용량 | 지표 이름, 범위, 단위, 수집 방법을 보존 |
| 힙 | 관리 힙·네이티브 힙 등 | 사용량 변화와 할당량을 동일한 값으로 취급하지 않음 |
| RAM | 디바이스 전체·가용 RAM 등 | 앱 메모리와 별도 범위로 표시 |
| 디스크 | 제공 가능한 읽기·쓰기 바이트·횟수·시간 | 프로세스/시스템/계측 호출 범위를 표시 |
| 렌더링 | 프레임 시간, Jank | OS·수집기·주사율에 따른 판정 기준을 보존 |
| 외부 연결 | 요청, 목적지, 응답, 오류, TTFB | 요청별 시각과 네트워크 이벤트를 연결 |
| 캐시 | 히트·미스·히트율 | 캐시 계층·대상·관측 구간과 분모를 표시 |
| 기기 | OS, 모델, 메모리, CPU 정보, 측정 조건 | 수집 가능한 사양·성능값과 실제 측정 결과를 구분 |
| 프로젝트 | 권한, 모듈·외부 의존성, RES, 테스트 | 구성 분석 결과이며 테스트 실행 결과와 구분 |

캐시 히트율은 현재 전체 요구사항에 포함되어 있다. 지원할 캐시 어댑터와 최종 시각화 배치는 후속 상세 설계가 필요하다.

## 수치 표현 규칙

- 함수 선택 구간에서 프로세스 메모리가 증가했다고 그 증가량을 해당 함수만의 할당량으로 단정하지 않는다.
- 프로세스 자원 시계열과 직접 계측한 함수별 수치를 구분한다.
- 짧은 함수 구간에 샘플이 없으면 측정 해상도의 한계로 표시한다.
- 미수집·미지원·수집 실패·이벤트 유실은 0과 구분한다.
- 다른 기기, OS, 빌드, 초기 상태, 캐시 상태의 결과를 조건 없이 합산하지 않는다.
- 기기 성능은 사양 정보와 실측값으로 제시한다. 근거가 정의되지 않은 단일 성능 점수는 만들지 않는다.

Android의 앱 시작 TTFD는 `reportFullyDrawn` 등의 앱 시작 측정 체계와 연결된다. 모든 Nav3 상태 도달 시간을 같은 공식 지표로 부르지 않고, 일반 화면은 별도의 준비·완료 규칙을 정의한다. [Android 앱 시작 시간](https://developer.android.com/topic/performance/issues/launch-time)

메모리·렌더링 수집 방법은 [Debug.MemoryInfo](https://developer.android.com/reference/android/os/Debug.MemoryInfo)와 [Android 렌더링 문서](https://developer.android.com/topic/performance/issues/render)를 기준으로 지원 OS별 검증 후 결정한다.
