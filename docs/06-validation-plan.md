# 검증 계획과 구현 순서

아래 시나리오는 전체 제품의 검증 계획이며 모두 통과한 테스트 목록은 아니다. 2026-10-13까지 실행한 정적 수집·보고서 검증은 별도로 구분한다.

2026-10-14 기준 플러그인 테스트 51개와 Compose 샘플의 전체 스냅샷·캐시·삭제·실패 처리, UI 진단·디자인 매칭 회귀를 검증했다. 룰업의 37개 모듈 결과에서 미연결 원인과 디자인 source anchor를 재검사했다. 단계별 입력·결과·제한은 [카탈로그 검증](09-catalog-decisions-and-validation.md), [분석 엔진 검증](10-sootup-heros-analysis.md), [UI 진단·디자인 대응 검증](11-ui-diagnosis-and-design-matching.md)을 따른다. 문맥별 부분 역할 분류는 구현했으며, 전체 화면·상태 분류, 이벤트·전환 분석과 화면 발견률 목표는 미완료다.

## 구현 순서

2026-10-15 보완: 화면 연결·접근 경로의 세부 단계와 반례는 [12번 설계](12-transition-and-access-path-design.md), 고객 코드의 실행·저장·외부 전송 차단 인수는 [13번 설계](13-local-analysis-security.md)를 따른다. 기능 테스트와 별도로 격리 환경의 정상 offline 분석, 금지 통신을 시도하는 합성 fixture, cache·로그·CI·viewer·디바이스·취소/실패 경로를 검증한다. 아래 기능 구현을 진행하더라도 격리 인수를 통과하기 전 비전송 보장을 제공하지 않는다. 신규 전환/격리 시험은 아직 수행하지 않았다.

| 단계 | 산출물 | 완료 기준 |
| --- | --- | --- |
| 1. 빌드 연동 PoC | 한 버전 조합의 Gradle·IR 플러그인 | 실제 variant 설정과 생성 소스를 반영한 수집용 컴파일 성공 |
| 2. 화면 발견 | 전체 Composable·UI 루트·Nav3 카탈로그와 분류 결과 | 루트 안팎·직접 provider·조건부·모듈 등록을 보존하고 삭제/캐시 복원 이후에도 일치 |
| 3. 전환 정적 분석 | host·UI 선택 상태·콜백·전환 후보 | 직접·Navigator·DI·이벤트 경유 전환을 구분하고 미해결을 보존 |
| 4. 실행 관측 | 실제 등록·표시·전환 이벤트 | 빌드·디바이스·화면 인스턴스별 정확한 연결 |
| 5. 함수·자원 계측 | 호출 이벤트·시계열 | 반복·비동기 호출 보존과 시간 기준 검증 |
| 6. 대시보드 연결 | 확정된 네 가지 화면 | 화면 상태 → 경로·디바이스 → 호출·자원으로 탐색 가능 |
| 7. 범위 확대 | 버전·라이브러리 어댑터 | 지원 표와 미지원 동작이 실제 검증 결과와 일치 |

## 화면 정의 발견률 99% 검증 목표

**SDUI를 제외한 지원 범위의 화면 정의 발견률 99% 이상**을 목표로 한다. 정적 수집기는 구현됐으나 화면 정의 정답 목록에 대한 발견률·정밀도와 정식 성능 벤치마크는 아직 측정하지 않았다. 이 목표는 모든 Android 프로젝트에 대한 보장이나 전환 경로 99% 발견을 뜻하지 않는다.

### 평가 집합과 정답 목록

1. 공개 샘플과 사용 허가를 받은 실제 프로젝트에서 commit, 앱 variant, AGP·Kotlin·Compose·Nav3·DI 버전을 고정한다. 직접 호출뿐 아니라 멀티모듈·DI·비동기·Nav3 밖 콘텐츠 패턴을 포함한다. [공식 Nav3 recipes](https://github.com/android/nav3-recipes)는 후보 자료이며, 선택한 commit의 의존 버전까지 기록한다.
2. 수집 결과와 독립적으로 사람이 소스와 등록·구성 관계를 검토해 화면 정의, 상태·컴포넌트, 콘텐츠·루트·provider 연결, 전환 경로의 정답 목록을 만든다. 실제 실행 이력만을 정답 목록으로 사용하지 않는다.
3. 화면 단위는 평가 전에 고정한다. 키·provider 맥락의 목적지와 Nav3 밖 독립 콘텐츠를 구분하고, 같은 화면의 인자 값·상태·래퍼를 각각 새 화면으로 세지 않는다. 같은 콘텐츠를 재사용하는 다른 목적지 맥락은 분리한다. 죽은 코드의 화면 정의와 미연결 등록도 정의 발견 평가에는 포함하되 실행 도달성은 별도 라벨로 남긴다.
4. source set·모듈·버전·패턴의 포함 범위와 SDUI·다른 variant·외부 바이너리 등 제외 범위를 분석 전에 기록한다. 범위 안에서 분석에 실패한 화면은 누락으로 세며, 결과를 보고 미지원으로 돌려 분모에서 빼지 않는다. 범위 밖 후보·공백도 별도 건수와 사유를 보고한다.
5. 자동 분석 결과를 먼저 평가한다. 사용자 수동 보정 후 결과는 별도로 보고하며 자동 발견률에 섞지 않는다. 미분류 목록에 Composable 이름만 있다는 이유로 화면 발견 성공으로 세지 않는다.

### 지표와 판정

| 지표 | 산식·판정 |
| --- | --- |
| 화면 정의 발견률 | 정답 화면과 일치한 자동 화면 정의 수 / 범위 내 정답 화면 수 = TP / (TP + FN). **99% 이상 목표** |
| 화면 판정 정밀도 | TP / (TP + FP). 상태·컴포넌트를 화면으로 잘못 분류하거나 중복 예측한 경우를 오탐으로 보고 |
| 화면 연결 해석률 | 정답 목록의 필수 콘텐츠·루트·provider·host 연결 중 올바르게 해석한 관계 수 / 해당 정답 관계 수. 관계 종류별로도 보고 |
| 전환 경로 발견률 | 정답 경로와 일치한 전환 후보 수 / 범위 내 정답 경로 수. 출발·목적·동작·조건·host 또는 표시 영역을 비교 |
| 전환 경로 정밀도 | 정답 경로와 일치한 후보 수 / 출력한 경로 후보 수. 근거 없는 구현·스트림 연결을 오탐으로 보고 |
| 분석 잔여 항목 | 미분류 콘텐츠, 연결 미해결, 불완전한 후보 집합, 분석 제한, 미분석 모듈·바이너리의 개수·원인 |

TP는 정답 정의의 콘텐츠·소스 위치와 목적지 또는 독립 화면 맥락이 일치할 때만 인정한다. 화면별 일대일 대응으로 계산하며 동일 정답에 대한 중복 예측은 추가 TP가 아니다. 루트나 provider의 일부 연결을 못 풀었더라도 화면 자체를 올바르게 식별했다면 발견 TP가 될 수 있으나, 그 관계는 연결 성공으로 세지 않는다. 원시 선언·미분류 후보 보존 건수는 별도 지표다.

연결 해석률의 분모는 발견된 화면만으로 만들지 않는다. 놓친 화면에 딸린 필수 정답 관계도 포함한다. 의도적으로 루트에 연결되지 않은 선언은 루트 연결 대상이 아님을 정답에 명시한다. 여러 대상을 가질 수 있는 관계는 정답의 조건별 후보 집합과 비교하고, 불완전하거나 과도한 후보 집합을 완료로 세지 않는다. 정밀도와 연결·경로 지표의 수치 인수 기준은 첫 평가 집합 확정 시 분석 실행 전에 별도로 정한다.

프로젝트별·패턴별 결과와 전체 TP·FN·FP 합계를 모두 보고한다. 전체 발견률은 프로젝트 백분율의 단순 평균이 아니라 합산 TP / 합산 정답 화면 수로 계산한다. 이 값이 99%여도 모든 프로젝트에서 99%라는 뜻은 아니다. 분모가 0이면 해당 없음으로 표시한다. 정답 목록이 없는 실제 사용자 프로젝트에는 발견률 대신 처리 범위와 미해결 건수를 표시한다.

### 결과 보고 형식

| 항목 | 기록할 내용 |
| --- | --- |
| 평가 입력 | 프로젝트·commit·variant·모듈, 지원 버전·패턴, 제외 범위와 사유 |
| 평가 조건 | 분석기·분류 규칙·정답 목록 버전, 자동/수동 보정 여부 |
| 화면 발견 | 정답 화면 수, TP·FN·FP, 발견률·정밀도, 누락·오탐 목록 |
| 연결·경로 | 관계 종류별 분모·성공 수, 경로 TP·FN·FP, 미해결 근거 |
| 실행 비용 | 전체·증분 수집 시간, 최대 메모리, 캐시 조건 |

작은 컴파일 예제로 IR에 키·람다·호출 관계가 남는 것을 확인하더라도 end-to-end 수집기나 99% 발견률 검증을 대체하지 않는다. MVP 동작 확인과 이 발견률 목표 달성 여부도 별도 보고한다.

## 빌드·캐시 시나리오

- clean 수집과 재실행 결과가 동일하다.
- 한 파일 변경 후 수정하지 않은 화면이 사라지지 않는다.
- 파일 삭제, 이름 변경, 파일 내 마지막 entry·Composable·UI 루트 제거 후 오래된 항목이 남지 않는다.
- 보조 함수의 내부 변경과 의존 모듈 변경이 결과에 반영된다.
- variant 변경 시 다른 variant의 결과가 섞이지 않는다.
- 생성 소스 변경과 제거를 반영한다.
- 컴파일 실패 후 부분 카탈로그를 성공 결과로 공개하지 않는다.
- 빌드 캐시 복원과 다른 작업 경로에서의 복원 결과가 일치한다.
- 병렬 모듈 실행이 출력 파일을 공유하지 않는다.
- 컴파일러·Compose·Nav3·분석기 버전 변경을 입력 변경으로 처리한다.
- 후속 증분 수집기는 전체 수집 기준 결과와 비교해 검증한다.

## 전환 분석 시나리오

- 직접 클릭에서 push하는 경로.
- 동일 출발·도착 화면으로 가는 서로 다른 버튼.
- 보조 함수, Navigator, ViewModel을 경유하는 경로.
- 함수 참조·고차 함수·다른 모듈로 전달된 콜백.
- 인터페이스 구현 후보가 여러 개인 경우.
- 같은 Navigator 타입이 서로 다른 qualifier·component·host에 주입되는 경우.
- DI 생성 소스·기여 함수가 다른 모듈에 있는 경우.
- Channel/Flow의 생산자·소비자를 거치는 경우와 같은 이벤트 타입의 서로 다른 스트림.
- 수집한 stack·UI 상태 변경에서 원인 화면을 역추적하는 경우.
- Nav3 밖 로그인 상태 변경과 콘텐츠 선택, 목적 host의 초기·복원 상태 연결.
- 구성 호출만 있고 전환 행동이 없는 경우에는 전환 간선을 만들지 않음.
- 조건에 따라 목적지가 달라지는 경우.
- mutable list 변경과 불변 리스트 교체.
- 목적 키는 알지만 인자 값은 동적인 경우.
- 이전 스택에 따라 목적지가 달라지는 back 동작.
- 딥링크로 초기 스택이 만들어지는 경우.
- 탭·중첩 host·다중 패널·다이얼로그.
- 상태 복원, 구성 변경, predictive back 취소.
- 시간상 가까우나 관계없는 두 행동과 전환.
- 비동기 처리 중 출발 화면이 사라진 경우.

각 시나리오는 전환 후보와 실제 관측이 일치하는지 검증한다. 미해결 관계가 사라지거나 잘못 확정되는 경우도 실패로 본다.

## 함수·자원·표시 시나리오

- 같은 함수의 반복 호출이 개별 행으로 보인다.
- 동기 부모·자식과 비동기 부모 관계를 구분한다.
- 코루틴 중단·재개·취소·예외를 기록한다.
- 함수의 경과 시간과 CPU 실행 시간을 혼동하지 않는다.
- 화면 컴포넌트 완료 이벤트가 같은 시계 기준으로 연결된다.
- 함수 선택 시 모든 자원 그래프의 같은 시간 범위가 강조된다.
- 샘플이 없는 짧은 호출을 자원 사용 0으로 표시하지 않는다.
- 자원 미지원·수집 실패·이벤트 유실을 구분한다.
- 외부 요청과 TTFB, 지원하는 캐시의 히트·미스를 관련 작업에 연결한다.
- 여러 기기의 세션이 섞이지 않으며 기기 성능과 조건을 확인할 수 있다.
- 계측 자체의 시간·메모리·CPU 오버헤드를 측정한다.

## MVP 인수 기준

1. 전체 Composable·UI 진입점·Nav3 연결을 결합해 화면 정의와 후보를 수집하고, 분류 근거·처리 범위·미해결 항목을 확인할 수 있다.
2. 화면·상태 지도에서 분석 범위를 선택할 수 있다.
3. 선택한 화면 상태의 인바운드 경로와 디바이스별 측정 결과를 확인할 수 있다.
4. 경로에서 함수 호출·UI 완료 시점·자원 시계열·외부 연결로 이동할 수 있다.
5. 구성 그래프에서 내부 모듈을 탐색하고 우측에서 외부 패키지·권한·RES·테스트 구성을 확인할 수 있다.
6. 측정하지 않았거나 해석하지 못한 정보를 측정값 또는 확정된 사실로 표시하지 않는다.

## 설계 변경 원칙

제품 요구사항, 기술 설계안, 검증 결과를 구분해 수정한다. 지원되지 않는 항목을 문서에서 조용히 제거하지 않고 지원 표와 진단 정책을 갱신한다. 이름·인터페이스·스키마가 확정되면 관련 문서와 예시를 함께 변경한다.
